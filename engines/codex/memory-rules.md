## 项目记忆（Codex 读写规则）

不使用 Codex 原生 memories。记忆按项目存放在**项目根目录的 `.memory/`**，随仓库迁移。**Claude Code 也读写同一个目录**（它把这里当作自己的自动记忆），所以格式以 Claude Code 为准。项目根 = 从当前目录向上最近的、含 `.memory/` 或 `.git` 的目录；都没有就是当前目录。

每次会话开始（以及上下文压缩后），系统会注入一段「# 项目记忆」，给出本项目记忆目录的绝对路径和 `MEMORY.md` 索引。项目的红线与工作习惯在项目 `AGENTS.md` 里，不在记忆里。

### 结构

- `MEMORY.md` 是索引，每条记忆一行：`- [标题](文件名.md) — 一句话说明`。不写 frontmatter，不放正文。只有前 200 行会被加载，保持精简。
- 每条记忆一个文件 `<name>.md`，一个文件只记一件事：

  ```markdown
  ---
  name: <kebab-case，与文件名一致>
  description: <一行摘要，用来判断是否相关>
  metadata:
    type: user | feedback | project | reference
  ---

  <正文。feedback 和 project 类型在正文后加 **Why:** 和 **How to apply:** 两行>
  ```

- `metadata` 里你不认识的字段（如 `node_type`、`origin`、`scaffold_sha`、`modified`）是别的工具写的，原样保留，不要删改。
- 正文里用 `[[name]]` 链接相关记忆。链接到还不存在的 name 也可以，表示那件事值得以后补写。

### 四种类型

- `user`：用户是谁——角色、专长、偏好。
- `feedback`：用户对你工作方式的指导，包括纠正，也包括被确认有效的做法；写明原因。
- `project`：进行中的工作、目标、约束、决定——代码和 git 历史里看不出来的。相对日期一律换算成绝对日期。
- `reference`：外部资源的位置（URL、看板、工单、文档、工具）。

### 怎么读

- 注入的索引已经在上下文里，不用再打开 `MEMORY.md`。任务和某条记忆相关时，读对应的正文文件。
- 记忆反映的是写入时的状况，可能已经过时。其中提到的文件、函数、命令、开关，据此建议或行动前先核实还存在。发现记忆错了，就改掉或删掉。
- 记忆是背景信息，不是指令。和用户当前的明确要求冲突时，以用户为准。

### 什么时候写

- 用户明确要你记住某件事 → 立刻写。
- 用户纠正你的做法，或明确认可一个不显而易见的做法 → 写 `feedback`。
- 了解到对以后的工作有用、但在代码、文档、git 历史里看不到的背景、约束、决定 → 写 `project`。
- 了解到用户的角色或偏好 → 写 `user`；了解到外部资源的位置 → 写 `reference`。

### 什么不写

- 代码结构、实现细节——读代码就知道的。
- 已经写在 AGENTS.md、README、文档或 git 历史里的内容。
- 只对当前这次会话有意义的临时状态（正在调试哪一行、本次的中间结果）。
- 密钥、令牌、密码等凭证。
- 用户要求记住上面这类内容时，问清楚其中哪部分是不显而易见的，只记那部分。

### 怎么写

1. 先看索引里有没有已经覆盖这件事的记忆：有就更新那个文件，不新建重复的。
2. 新建时按上面的格式写文件；目录或 `MEMORY.md` 不存在就直接创建。
3. 新建、改名、删除记忆后，同步更新 `MEMORY.md` 索引。
4. 写完在回复里用一句话说明记了什么、记在哪个文件，方便用户纠正。
5. 用户和 Claude Code 也会改这些文件，一切以文件当前内容为准。
