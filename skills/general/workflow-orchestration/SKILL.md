# workflow-orchestration:以 Workflow 为核心锚点的工程编排

> **你是多 agent 编排的操盘手。核心信念:单 agent 单次输出 = 一个误差未知的点估计;N 个独立 agent = 集成(ensemble),独立性让不相关误差相互抵消——Workflow 改的是每份产出的「认识论地位」,不只是速度。铁律:fan-out 的是劳动,fan-in 的判断永远留在你手里——`agents propose, orchestrator disposes`,唯一不可外包的是最终裁决。**

深层第一性原理与每种范式的完整 grounding 见 Multica `above-the-wind` 方法论簇(hub ATW-26 · 5 支 ATW-28~32 · 配合锚 ATW-27)——**可选、个人 workspace、非复用必需**:本 skill 的决策流不查它也能照跑,深参考只是加分。

## 怎么用(决策流)

### Step 0 · 要不要上 workflow(杠杆闸)
- 单事实 / 单文件的琐碎活 → 单步搜索或直接干,**别开编排**。
- 值得上的信号:方案空间宽、要多视角证伪、规模大要并行、重活压主上下文。**值才上。**
- ultracode / 大任务可默认常开;但"默认开" ≠ 无脑 5-agent 轰一切——**按杠杆定规模**(边际视角≈免费但有拐点)。

### Step 1 · 选形状(按依赖结构,别一刀切)
- 子任务**相互独立** → **barrier fan-out**(`parallel`,一轮收齐)。
- 阶段间**有依赖** → **pipeline**(每站输出 = 下站输入 schema,可断点续跑)。
- **单个重活** → 只 **offload**(丢后台返 digest,保主上下文,压根不必并行)。

### Step 2 · 选范式(五选一或组合)
| 范式 | 什么时候 | 收敛机制 |
|---|---|---|
| **大规模调研 + 交叉验证** | 要吃透外部事实 / 许可 / 竞品 | 对外部事实交叉印证到「无冲突」→ **落成可复现脚本 + 数据**,不出散文 |
| **判官团(发散)** | 方案空间宽、要创造性方向 | N 路**不同框架** → 合成 + **嫁接各家最优**(暴露 dissent,不抹平) |
| **对抗审查(收敛)** | 已有产物要挑错、降返修 | N 个独立 lens(**含"完备性"一路**)→ 结构化 findings(带严重度+verdict) |
| **并行 + 上下文卸载** | 一批独立子任务 / 重活压上下文 | 提吞吐 + 护主判断力;**但并行 ≠ 真独立** |
| **大切片流水线** | 完整功能从 0 到合并 | 调研→判官团→build→闭环校验→对抗审查→蒸馏,阶段间走交接契约 |

发散(判官团)与收敛(对抗审查)矢量相反,**分开跑,别捆一坨**。两种「收敛」也别混:调研的收敛 = 对**外部事实**交叉印证到无冲突;对抗审查的收敛 = 对**自己产物**证伪。流水线里 **skill × workflow 互补**:确定性的品味 / 流程 skill(如 impeccable)嵌进某工位定「好的样子」,workflow 供多路独立视角逼近它——不是二选一。

### Step 3 · 收敛(劳动可 fan-out,fan-in 的最终裁决不可外包)
- 收敛阶段本身照样 fan-out N 个 lens / skeptic;**唯一不可外包的是 fan-in 那一下——最终裁决留在主控**。
- sub-agent 产出**必经主控逐条 verify 才算数**——结构化 findings 才好逐条消费。潜伏 bug 常是 verify 抓的、不是 lens 抓的。
- 收敛判据:**不设固定轮数,审到连续一轮无实质新发现即停**。
- 落到真实环境取证:前端走 **Playwright 闭环校验**(截图→读图→判断→改→再截,桌面/平板/移动/高视口多档 + 交互),后端走 **run-app + read-logs**。截图不读回来 = 没验证。**iOS 侧的取证分层与实测踩坑见 `ios-verify-loop`**(编译 / 模拟器 AXe 驱动 / 手势探针 / 只读 SQL 对账)。

**结构化产出契约长这样**(让主控能逐条 verify 的最小形状,别收散文):
```json
{ "findings": [ { "severity": "blocker|major|minor|nit", "location": "file:line 或选择器",
                  "issue": "可复现的失败场景", "fix": "具体修法", "verdict": "CONFIRMED|PLAUSIBLE" } ],
  "overall": "一句话总评" }
```
主控按 severity 排序 → 逐条 verify(CONFIRMED 才认)→ fix;判官团则回各方案的多维评分 + 暴露 dissent。

## Step 4 · 长跑可靠性(编排为什么会死,怎么不死)

> 上面三步管**怎么设计**编排;这一步管**编排真跑起来会怎么挂**。全部来自实测:两轮 60+ agent / ~6M token / 跨 4 次中断续跑,以及一次烧穿账号额度的事故。**设计得再对,死在这些地方一样交白卷。**

### 4.1 头号杀手:单点输出爆量(表现为「卡住」)

**症状**:workflow token 计数长时间不动,像死了。**真相**:某个 agent 要一次性吐出巨大结构化产出 —— **输入不是瓶颈,输出才是**。

**判据**:同一位置连挂两次 = 结构问题,不是运气。

**★ 总原则:任何需要 agent「重新输出一遍完整结构」的地方都是炸弹。** 一律改成**补丁式 + 代码组装**:

| 原做法(炸) | 改法(稳) |
|---|---|
| 吐完整 taxonomy / 完整清单 | 只返回 `{patches:[{key, add:[], drop:[]}]}`,JS 施加 |
| 跨项去重后吐全量 | 只返回 `{drop:[], rename:[]}` 指令清单,JS 执行 |
| 定稿时吐完整结构 | 只返回**逐项判决**,其余由代码从上一版承继 |
| 让 LLM「生成」join 得出的字段 | **根本不该让 LLM 生成** —— 直接在 JS 里写成常量,让 agent 生成纯属浪费还容易编 |

**★ 修了一处,必须主动去找其余同类。** 实测:修好 `merge` 的输出爆量后没排查同类,`expand` 用完全一样的方式挂了第二次;后来量产打标又以第三种形态复发 —— 同一个病付了三次学费。

### 4.2 量产管线:分小批写文件,返回只带计数

**永远不要让 agent 一次性返回大结构化 JSON。** 大 JSON 架构实测三种死法(全部真实发生):

| 死法 | 症状 | 证据形态 |
|---|---|---|
| ① 校验失败静默重试 | 分片任务反复重启才出 1 片,token 白烧(某次终局:**10 个分片 / 29 次 started / 1 条 result**,单片最多重启 4 次) | `journal started ≫ result` |
| ② 用户打断穿透 | 主控按 ESC,**打断信号穿透到后台 agent 的在途请求**,外面看是「idle 很久」 | transcript 末条 = `[Request interrupted by user]` |
| ③ 流断挂死 | N 个分片**同时**停在相同 token 数、idle 数分钟 —— 全死在吐大 JSON 那次生成,流断无重试 | 进度图齐刷刷同一数值 |

**v2 文件落盘架构(照抄)** —— 实测 **4/4 零失败零重试、0 校验错误、16.8 分钟**:
```
每 agent 领 N 条
  → 每 25 条一次 Write 写独立 jsonl 批文件(单次生成永远是小块)
  → 写完 wc -l 自查行数 == 领的条数,缺了补写
  → 最终返回只有 {slice, written, junk, batch_files}(几十字节)
  → 校验挪到代码侧:读文件验合法性 / 基数 / 键齐全 / 行覆盖,缺行重派单片
```
⚠️ **分工别搞错:workflow 脚本本身没有文件系统 / Node API**(`Date.now()`、`Math.random()` 同样被禁,写 `require('fs')` 直接挂)。所以 `wc -l` 自查是**写进 agent 的 prompt 里**(agent 有 Bash),脚本里只 `reduce` 汇总计数;**真正的读文件校验发生在 workflow 返回之后、由主控自己跑**,重派 = 再起一次 workflow。

三个结构性红利:**中途可观测**(随时 `wc -l` 看进度、抽分布;大 JSON 是黑箱到最后一刻)/ **失败爆炸半径 = 单片** / **断点天然友好**(落盘即持久,与 workflow 缓存双保险)。

### 4.3 并行分片必须配全局产出预算

分片让每个 agent 看不见全局 —— 这既是它的优点(输出小),**也是它的风险(没人管总量)**。

实测:7 个并行合并 agent 互相看不见、又都被指示「宁滥勿缺」,合出 **93 个维度**;下游实际只用了 9-10 维,**覆盖率静默地只覆盖 10%**,而报表把没跑过的维度印成「缺口 0.0%」。

**规则:并行分片必须配全局约束(每片最多 N 个产出),否则「宁滥勿缺」× N 片 = 爆炸。**

### 4.4 失败是常态,不是异常

长跑里 agent 失败**必然发生**(实测遇到:`Response stalled mid-stream`、超 64k 输出上限)。

- **每个消费 agent 返回值的地方都要接得住 `null`**。踩过:一个 agent 返回 null → 渲染函数直接抛 → **整条 workflow 崩掉,后面十几个 agent 一个没跑**。
- 修好 null 兜底后再遇 agent 失败,**流程正常走完、只少一个产物** —— 这才是正确形态。
- 关键节点给降级路径。

### 4.5 指标由代码算,且区分「没数据」和「零」

- **绝不让 agent 自评指标**(覆盖率 / 一致性)—— 它只会说「覆盖良好」。指标一律用代码从 agent 的**原始结构化产出**里统计。
- **★ 给「没数据」和「数据显示为零」不同的表示**(如 sentinel `-1.0`)。**两者在报表上长得一样,含义完全相反** —— 正是这个 sentinel 暴露了「83 维根本没跑过」的静默失败。

### 4.6 用 LLM 当评测者的边界

- **金标集必须人工。** 让 LLM 交叉标注测「一致性」,测出来的是同一模型族在同一 prompt 下的**自一致性**,不是标注者间信度。
- **结论不对称**:**负面结论可信**(模型没动机集体编出「这套方案不好用」),**正面结论不可信**(不能说「这维拿了 0.884,最稳」)。
- 一句话:**LLM 交叉标注可以用来证伪,不能用来证实。**
- 连续值别用 Jaccard 做精确串比(`0.5` 与 `0.50` 会算不一致,跑出假低分),该用相关系数。

### 4.7 缓存续跑纪律

- **缓存 key 是前缀链,不是单点** —— key = `hash(前序调用链 + prompt + opts)`。所以**只改最后几步零损失**(实测改了三处后,前面 21 个 agent 全部瞬间从缓存返回,四次中断零重跑损失),但**任何上游改动都会让它之后全部失效** —— 包括在中间插一个新 agent、重排顺序、改前面某个 agent 的 `effort`,不只是改 prompt 文字。
- **★ 改脚本前必须确认上游一字未动。** 每次 resume 前 `grep` 一遍锚点。
- ⚠️ **一旦发生首次 miss,该 run 之后所有 agent 一律不再查缓存** —— 别指望「中间改一处、后面还能捡回来几个」。
- 脚本落盘是 `.js`(按 CJS 解析,顶层 `return` 本来就合法),**`node --check` 可以用,是很便宜的语法闸,跑一次 workflow 是要花钱的**;别用 `.mjs` / `--input-type=module` 去检,那样顶层 `return` 才会误报。

### 4.8 诊断「卡住」:三义辨析

**必须看 transcript 最后一条实质输出**,别看别的:

| 现象 | 真相 | 该做什么 |
|---|---|---|
| 文件 mtime 很久没动 | **正常** —— agent 生成期间没有工具调用就不写盘(7 分钟不写盘常见) | 别杀 |
| 末条 = `[Request interrupted by user]` | 被打断的死尸 | 等不来了,重派 |
| 末条是工具结果、无后续 | 流断挂死 | 重派 |

⚠️ **`journal.jsonl` 的 `started` − `result` 差值会骗人**:被停掉 / 断网杀掉的 run 只留 `started` 不留 `result`,**永远算「在跑」**(实测看到「8 个在跑」,实际只有 3 个活的)。另:journal 的结果字段是 `result` 不是 `value`。

### 4.9 effort 继承与越权动手

- **子 agent 默认继承会话推理档** —— 开着 ultracode/xhigh 时,机械执行类活(按定义打标、格式转换)会被高档拖慢还烧钱。**机械 agent 一律显式 `effort: 'medium'` 降档**,探针证实质量无损。
- **agent 会超出授权范围动手**:prompt 写的是「给出 diff」,agent 直接把改动应用到了工作树。**要写文件的 workflow 跑 `isolation: 'worktree'`**,或在 prompt 里明确禁止写入。

### 4.10 放量前的资源 gate(最贵的一课)

事故:试点验证通过后发全量,发车前报了「~74M token / ~7 小时 / 16 并发」,据此放行 —— 实际**跑了不到 10 片(< 2.4%)额度就见底**,大批切片失败。若不是账号主人中途回来看了一眼,当天所有工作都会被这一个任务吃光。

三条规则,逐条更根本:

1. **★ 资源三件套:消耗量 / 占总配额比例 / 对其他工作的挤出效应。只报第一项等于没报。** 「74M token」这个数字是对的,但它是「资源消耗量」,不是「你还能不能干别的」。
2. **风控自检**:批量调用类任务除了算钱算时间,还要问一句「**这个调用模式看起来像什么**」。单账号短时间大批量结构化加工,行为特征接近蒸馏 / 数据加工,有触发平台风控的现实可能 —— **账号被封的期望损失远大于产出收益**。
3. **★ 试点只能证明「做法对」,不能证明「做得起」。** 试点验证的是**架构可靠性**,不是**资源可行性**,这两件事在 4 片和 419 片之间是**非线性**的。**放量前必须单独回答一次资源问题,且答案不能由跑试点的人自己拍板 —— 它属于账号主人。**

另两条配套:
- **便宜路先探底**:当便宜方案与昂贵方案能达成相近效果时,**默认先把便宜方案做到底、量出天花板**,再论证是否需要昂贵的。(那次事故后回落到零 LLM 的规则 + join 方案,几秒钟出全量结果,产品效果足够 —— 零 LLM 本该是第一选择,不是降级选择。)
- **可中止性**:大任务必须能在任意时刻中止且**已完成部分不丢**(落盘即持久)。事故里 3,049 条已完成产物全部留在盘上并二次利用。

### 4.11 全量前压测清单(照抄勾选)

- [ ] 单片体量:单次生成 ≤ ~25 条结构化内容(或等价 token)
- [ ] 输出走文件,返回只带计数;`wc -l` 自查写进 prompt
- [ ] 校验在代码侧,失败重派粒度 = 单片
- [ ] 每个消费返回值处接得住 null
- [ ] 并行分片配了全局产出预算
- [ ] 机械 agent 显式 effort 降档
- [ ] 跨架构 / 跨档探针跑过,一致度不掉(逐维 Jaccard 或相关系数)
- [ ] 分布哨兵:前 N 片先查形状(垃圾桶值 / 未用值 / junk 率)
- [ ] 指标由代码算,「没数据」与「零」表示不同
- [ ] 资源三件套已报,放量 gate 已由账号主人拍板
- [ ] 网络:量产长跑换稳定网络(热点上的流断实测过)

## 硬性规则

1. **agents propose, orchestrator disposes** — sub-agent 产出必经主控 verify;最终裁决永不外包。fan-out 不配 verify,就是把不可信产出放大 N 倍。
2. **结构化产出契约** — 让 sub-agent 回结构化(findings 带严重度/verdict、评分、schema),主控才能确定性逐条消费,也才可回流 issue、可审计;**不收散文**。
3. **独立性是承重假设、会被破坏** — 共享 repo / 文件 state 泄漏会制造相关失败;并行拿到 0 error 后**主控串行复审仍强制**。跨 lens / 跨引擎的独立 > 同质多开。
4. **过量供给视角、但有拐点** — 边际 reviewer ≈ 免费故审查量应往上调;但 token / 时间有限,收益递减处刹车。⚠️「免费」只在**审查规模**这一档成立;**量产 / 放量另走规则 12 的资源 gate** —— 那一档边际 agent 一点都不免费。
5. **上下文卫生** — 重活丢后台,护 orchestrator 的上下文(它是唯一稀缺资源、= 判断质量)。
6. **收敛判据成文** — 审到连续一轮无实质新发现即停;不设固定轮数、也不草草一轮。
7. **不让 agent 重吐完整结构** — 改补丁式 + 代码组装;修好一处**必须主动排查同类**(同一个病实测复发过三次)。
8. **量产走文件落盘、返回只带计数** — 校验挪代码侧,失败重派粒度 = 单片;别让单次生成扛大 JSON。
9. **失败是常态** — 每个消费返回值处接得住 null,关键节点给降级路径;一个 null 能崩掉整条 workflow。
10. **指标由代码算,「没数据」≠「零」** — 别让 agent 自评;两者报表上长得一样、含义相反。
11. **LLM 交叉标注只能证伪、不能证实** — 金标必须人工;负面结论可信,正面结论不可信。
12. **放量前过资源 gate** — 报**三件套**(消耗量 / 占配额比 / 挤出效应),只报第一项等于没报;**试点只证明「做法对」不证明「做得起」,放量拍板权属于账号主人**。

## 反模式

❌ 琐碎活也开 5-agent → 按杠杆定规模,值才上。
❌ 拿 sub-agent 产出直接当结论 → 必经主控逐条 verify(agents propose, orchestrator disposes)。
❌ lens 自己收口就算审完 → fan-in 的判断留主控;lens 只提怀疑,主控取证裁决。
❌ N 路同质多开当"独立视角" → 给每路不同框架 / lens 逼真发散,独立性才承重。
❌ sub-agent 回散文 → 要结构化(findings / 评分 / schema)才能确定性消费。
❌ 并行 0 error 就以为可信 → 共享 state 会泄漏,主控串行复审强制。
❌ 前端改完只看代码 / 类型检查 → 上 Playwright 真实环境截图取证。
❌ 把发散(判官团)和收敛(对抗审查)糊成"一种评审" → 矢量相反,分两枝跑。
❌ 让某个 agent「把 N 份结果合成一份完整结构」→ 输出爆量必挂;改补丁式 + 代码组装。
❌ 修好一处输出爆量就收工 → 同类必然还有,主动去找(实测复发三次)。
❌ 量产让 agent 一次返回 50 条大 JSON → 三种死法(校验重试 / 打断穿透 / 流断)全遇过;走文件落盘。
❌ 让 LLM 生成 join 得出的字段 → 代码里写常量,让它生成纯属浪费还容易编。
❌ 并行分片各自「宁滥宁缺」不设总量 → 「宁滥」× N 片 = 维度爆炸,下游静默只用 10%。
❌ 看文件 mtime 判断 agent 死没死 → 生成期不写盘是正常的;看 transcript 末条实质输出。
❌ 拿 journal 的 started−result 差算「几个在跑」→ 死尸只留 started,会把在跑数虚报高。
❌ 让 agent 自己汇报覆盖率 / 一致性 → 它只会说「覆盖良好」;指标由代码算。
❌ 用 LLM 交叉标注证明「标得准」→ 只能证伪不能证实;金标必须人工。
❌ 机械执行类 agent 吃继承的 xhigh → 显式降 medium,质量无损、省时省钱。
❌ 要写文件的 workflow 直接跑在主工作树 → 子 agent 默认落在 `acceptEdits`,会不问就写;**优先在 prompt 里明确禁止写入**(零成本),只有多 agent 并行改同一批文件才上 `isolation: 'worktree'`(每 agent ~200-500ms + 磁盘开销)。
❌ 试点跑通就发全量 → 试点证「做法对」不证「做得起」;放量前单独过资源 gate,拍板权归账号主人。
❌ 报预算只报「要烧多少 token」 → 必须同时报占配额比例与对其他工作的挤出效应。

## 常见问题

| 症状 | 原因 | 解决 |
|---|---|---|
| workflow 产出看着对、一集成就错 | 没主控 verify,或 sub-agent 共享 state 泄漏 | 逐条 verify;排查跨 agent 的 state 依赖 |
| 多路 agent 给的方案都差不多 | 没给不同框架,同质多开 | 每路指定不同出发框架 / lens |
| 审查没完没了 / 草草一轮 | 没定收敛判据 | 连续一轮无实质新发现即停 |
| 主上下文被 sub-agent 输出撑爆 | 没走结构化 / 没卸载 | 结构化 schema 回收 + 重活丢后台返 digest |
| 前端"应该没问题"但真跑有 bug | 只静态看没跑真实环境 | Playwright 多档视口截图 + 交互实测 |
| 小任务也开一堆 agent、又慢又费 | 没过杠杆闸 | Step 0 先判值不值得,琐碎活单步干 |
| workflow token 计数长时间不动、像死了 | 某 agent 在吐超大结构化产出(输出爆量) | 4.1:改补丁式 + 代码组装;同位置连挂两次 = 结构问题 |
| 同一个爆量问题修完又在别处复发 | 只修了发现的那处 | 4.1:修一处主动排查全部同类 |
| 量产分片大批失败 / 反复重试烧 token | 单次生成扛大 JSON | 4.2:分小批写文件,返回只带计数,校验挪代码侧 |
| 整条 workflow 崩掉、后面 agent 一个没跑 | 某处没接住 agent 返回的 null | 4.4:每个消费点接 null,关键节点给降级 |
| 报表显示「缺口 0.0%」但其实根本没跑 | 「没数据」与「零」用了同一种表示 | 4.5:给没数据设 sentinel,指标由代码算 |
| 一致性分数很漂亮,但结论站不住 | 用 LLM 交叉标注去「证实」 | 4.6:只能证伪;金标人工;连续值用相关系数 |
| resume 后前面的 agent 全部重跑 | 上游 prompt 被改动,缓存失效 | 4.7:改脚本前 grep 确认上游一字未动 |
| 看着「8 个在跑」实际只有 3 个 | journal 死尸只留 started 不留 result | 4.8:看 transcript 末条实质输出 |
| 机械打标又慢又贵 | 子 agent 继承了会话的 xhigh | 4.9:显式 `effort: 'medium'` |
| agent 把改动直接写进了工作树 | 未隔离 / prompt 没禁写 | 4.9:`isolation: 'worktree'` 或明确禁止写入 |
| 试点很顺,放量却烧穿额度 | 试点只验了架构、没验资源 | 4.10:放量前单独过资源三件套 + gate 归账号主人 |
