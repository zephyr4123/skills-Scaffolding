# zephyr-secrets-hygiene

> 把「一台开发机上的密钥怎么才算管得住」从一次真实的全机整理里蒸馏成可复用的治理法 —— 给的是判断方法与参考实现，不是可执行文件 —— 归位与退役本质是判断，包成命令反而危险。

## 问题陈述

开发机上的凭据是**攒出来的**，不是设计出来的：换公司、换项目、换电脑，每次留下一层。等到想起来整理时，典型现场长这样 ——

- 主目录里 14 个 600 权限的 `.env` 看着很规范，但 `.zshrc` 里三行 `export` 把它们全绕过去了：**所有防线都在，有人从旁边开了个洞**。任何 npm postinstall、任何 agent、任何第三方 CLI 都读得到。
- 三个同名 token，**值全不一样**。没人知道哪个是活的 —— 既不敢删也不敢用。
- 一把「看着像旧的」ssh 私钥，`~/.ssh/config` 里只挂着两台废机器 —— 而它真正的使用者写在某个项目的 toml 里。**只查配置文件就删，直接断掉线上部署。**
- 登记册漏登五份文件。不是懒，是**人工维护的清单必然漂移**。

更麻烦的是这个领域的**假阴性密度特别高**：安全工具倾向于"失败时静默"（不给攻击者信息），所以它们也对你静默。`ssh-keygen -p` 在非 TTY 下会把口令**静默设成空**，还照样打印 `saved with the new passphrase` —— 成功信息是真的，口令是空的。

结果：**整理这件事本身成了高风险操作**，而不整理又在持续渗漏。

## 解决方案

一套**四模式治理法**（审计 / 归位 / 退役 / 新增），纯方法论 + 参考实现：

- **归位靠一张分层表**，唯一维度是"这一刻有多少东西能读到它"，不是"这是 GitHub 的还是数据库的"。**第 0 层是「根本不存」** —— 能换成 SSO / OAuth / 短期会话的一律换，这比任何"藏得好"都强。
- **退役靠两条硬纪律**：查真正的调用方（不是查配置文件）、否定判断前先确认命令真跑成功了。删一律 `mv` 进隔离区，不 `rm`。
- **审计给的是扫描位置表 + 「只吐键名不吐值」的命令写法**。"绝不输出密钥值"没有代码兜底，所以直接给安全的命令形式，并点名 `grep -rn` 这类会把值整行打出来的写法。
- **按需加载器给参考实现，让用户写进自己的环境**。它不是配套工具，是**第 2 层能不能成立的前提**（见下一节）。

## 核心立论

**光禁止 `export` 是没用的。**

那三行 `export` 不是疏忽，是**真实需求踩出来的 desire path** —— 当初写它的心情是"每次 source 太烦了"。这个念头本身没错，错在它悄悄把安全模型从"按需授权"改成了"全局可见"，而这个改动没有任何地方记录。

所以立牌子（"以后不许 export"）没用，**把路修到人本来就想走的地方**才有用：`withkey figma curl …` 必须比 `export` 更省事 —— 不用记路径、不用记文件全名、用完自动散。

> **判断一条安全规矩会不会活下来，只问一句：遵守它的人，是不是比不遵守的人更省事？**
> 如果答案是"不是，但他应该有觉悟" —— 那这条规矩已经死了，只是还没人发现。

这条原则本身是元行为，已提炼进 `scaffold/HABITS.md`；本 skill 只讲它在密钥场景怎么落地，以及**它的边界** —— 有些歪路（`--force`、跳过 dry-run）收益当场兑现、代价延后转嫁给别人，修路救不了，只能焊死。

## 设计决策

| 决策 | 选择 | 原因 | 替代方案 |
|---|---|---|---|
| 分类维度 | 按**暴露面**分层，不按密钥类型 | 密钥治理唯一的变量就是"谁能读到"。按"GitHub 的 / 数据库的"分类，分完还是不知道该放哪 | 按服务商分目录 —— 分完等于没分 |
| 审计形态 | **位置表 + 安全的命令写法** | 要扫哪些位置随环境变，固定脚本会让人以为"跑过了 = 扫全了"。给命令形式比给可执行文件更能迁移 | 发一个 scan 脚本 —— 默认值写死，且掩盖覆盖面问题 |
| 加载器 | **必须给参考实现**，且要比 `export` 好用 | 没有可用替代品，"不许 export"就是空话，三个月后一定被加回来。但放哪、叫什么该由用户的机器定 | 发一份带死默认值的 loader —— 替所有人做了决定，还要长期背跨 shell 兼容 |
| 删除动作 | 一律 `mv` 进隔离区 | 判错的代价（断生产）远大于隔离的成本（几乎为零） | `rm` —— 不可逆，且这一节本来就最容易判错 |
| 同名多值判定 | **只提示不判死**（除非一处在 shell 启动文件） | 两个文件服务两个不同实体时，同名不同值是正常的。会误报的检查会被忽略 | 一律判红 —— 实测在两把 ASC key 上就误报了 |
| 机器布局 | **不写进本 skill** | skill 会进 git。布局归本机登记册（不进任何 repo），方法论才进仓库 | 把实例写进 skill —— 自己违反自己第一条铁律 |
| 平台 | macOS 优先，命令示例给等价物 | `security` / `stat -f` / `UseKeychain` 是 macOS 专有；但分层模型与全部纪律跨平台成立 | 只写通用命令 —— 会丢掉 keychain 这最安全的一档 |

## 已放弃方案

### A：把「修路 vs 焊死」原则完整留在本 skill 里
- **是什么**：把 paved-road 设计哲学连同判据表一起写进 SKILL.md。
- **为什么放弃**：它是**无论做什么活都适用**的元行为（立任何一条工程规矩、设计任何一道 guardrail 都在用它），按 HABITS.md 自己定的分层规则，该进常驻层而不是场景 skill。留在这里的代价是它只在密钥场景可见。**已入 HABITS 元行为层，本 skill 保留一节指回去。**

### B：把 shell 通用陷阱（`grep -c` 退出码、`zsh -i -c` 继承环境）拆去 `zephyr-quality-discipline`
- **是什么**：这三条不限于密钥场景，凡做否定判断都适用，理论上属于排查纪律。
- **为什么放弃**：它们是在密钥审计里撞到的、且高度具体；拆过去会让两个 skill 都变模糊，也构成范围蔓延。**留在本 skill 第五节，点明"不限于密钥场景"并 link 到 `zephyr-quality-discipline`，不改那个 skill。**

### C：做成 `secrets` CLI（子命令式，像 `zephyr-multica-read` 那样）
- **是什么**：`secrets scan / layer / retire / add` 一套子命令。
- **为什么放弃**：治理动作里真正可自动化的只有"审计"和"加载"两件，剩下的（归位判断、退役判断）**本质是判断不是执行**。包成子命令会让它们看起来可以自动做，而退役判断恰恰是这套流程里出错代价最高的一步。一份判断 playbook + 参考实现，是诚实的形态。
