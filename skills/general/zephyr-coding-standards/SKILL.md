# zephyr-coding-standards：把代码当作品写

> **心法：每一行代码都要有存在的理由。可删的代码就是该删的代码。**

按高级全栈工程师、高级软件架构师的水准产出。以下原则与语言、技术栈无关。

> 🔴 **硬规则（密钥不进代码、环境必隔离、破坏性变更必须可回滚等）在 HABITS 的「红线」节，那里是权威副本，本 skill 不重复。** 这里讲的是方法论——照做会更好，但不照做不会立刻造成损害的那些。

## 总则

- **不为写而写** —— 每一行都要有存在的理由；可删的代码就是该删的代码。
- **融入现有代码** —— 跟随项目既有的命名、结构与惯例，不另起炉灶。**判据：新增代码混在旧代码里，看不出是后加的。**

## 结构：三个清晰

| 维度 | 标准 | 怎么自检 |
|---|---|---|
| **目录清晰** | 包括文档的归置 | 任何人打开仓库，**能猜到东西在哪** |
| **结构清晰** | 分层明确（如界面 / 业务 / 数据），依赖**只指向一个方向** | 画一遍依赖图，**不出现环** |
| **模块清晰** | 单一职责、高内聚低耦合，模块间靠明确接口通信 | 每个模块能**独立理解、独立测试、独立替换** |

「独立替换」是最严的那一条——做不到，说明耦合还在。

## 设计

- **善用设计模式** —— 用对口的模式解决对口的问题，**不为了用模式而用模式**。
- **不过度设计** —— 为当前需求实现，为**可预见的**变化留缝，不给想象中的需求造抽象。

两条是一对张力：前者防"土法炼钢"，后者防"抽象癖"。判断落点看**这个变化是否已经有据可循**——有真实的第二个用例才抽象，只有一个用例时先写死。

## 实现

- **可读性优先** —— 代码首先是写给人读的。命名讲人话；函数和文件保持**一眼能读完**的规模。
- **错误处理显式** —— 失败路径认真设计。边界条件（空值、越界、并发、超时）**想在前面**，不是等它炸了再补。
- **为排查而留日志** —— 关键路径写结构化日志（带上下文与关联信息）。错误日志必须含定位所需的信息——**日志是写给三个月后排障的人的**，那个人很可能就是你自己。
- **性能靠测量** —— 先正确、后优化；优化必须有**测量数据**支撑，不凭感觉调。

## 留痕与文档

- **注释用中文**，写"**为什么**这么做"，不复述代码"在做什么"（协作项目已有英文注释惯例的跟随惯例）。
- **文档随代码同步更新** —— **过期的文档比没有文档更糟**，因为它会主动误导。
- **门面文档要好看** —— README 首先让人**五分钟内明白"是什么、怎么装、怎么跑"**；在支持 HTML 渲染的平台（如 GitHub）善用 HTML 美化（居中标题、徽章、表格布局、折叠详情），不要只用朴素 Markdown。

## 依赖与选型：站在巨人的肩膀上

- **成熟库优先** —— 能用成熟第三方库解决的不手写（几行代码能写清的琐碎功能除外），把精力留给**业务真正独有的逻辑**。
- **选型四看**：维护活跃度 · 社区规模 · 许可证 · 安全记录。
- **依赖锁版本** —— 用锁文件固定版本，定期升级与审计。
- **复用同理** —— 能复用现有 skill、脚本、模式的，不要重新发明。

## 环境与部署

- **环境必隔离** —— 任何语言的依赖都装在项目局部，不污染全局（🔴 这条是红线，见 HABITS）。
- **容器化思维** —— 模块边界要像容器一样清晰可拆装；服务类、需部署的项目优先用 Docker/K8s 等容器化交付。CLI 工具、纯库等不适用的项目**不强上**。
- **变更要可回滚** —— 破坏性变更（数据 schema、对外 API）必须有迁移方案和回滚路径；对外契约的不兼容变更**走弃用周期，不直接 break**。

## 反模式

❌ 为了"以后可能要扩展"先造三层抽象 → 只有一个用例时先写死，有了真实的第二个用例再抽象。
❌ 新代码另起一套命名/结构，跟项目原有风格并行 → 融入，不是并存。
❌ `catch` 完什么都不做 / 只打一行没有上下文的日志 → 失败路径要么处理要么向上抛，别让它静默消失。
❌ 日志只写"出错了" → 写清是什么请求、什么输入、什么状态，能让三个月后的人定位。
❌ 凭感觉做性能优化 → 先测量，拿数据说话。
❌ 手写一个成熟库已经解决的东西 → 除非那是业务独有逻辑。
❌ 改完代码不动文档 → 过期文档比没有更糟。
❌ 数据 schema 直接改、对外 API 直接删字段 → 走迁移与弃用周期。

## 交付前自检

- [ ] 新增代码风格与项目原有一致，看不出是"外挂"的
- [ ] 依赖方向单一，没有引入环
- [ ] 每个新模块能独立测试
- [ ] 失败路径与边界条件都想过并写了
- [ ] 关键路径有能定位问题的结构化日志
- [ ] 新依赖过了「四看」，版本锁了
- [ ] 改了行为的地方，文档同步改了
- [ ] 破坏性变更有迁移方案和回滚路径
- [ ] 可删的代码删干净了（注释掉的旧实现、没人调的函数）
