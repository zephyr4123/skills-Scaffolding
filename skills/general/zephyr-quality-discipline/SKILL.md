# zephyr-quality-discipline：质量不由写的人自证

> **心法：代码好不好，由测试说明、由对抗性审查说明、由实际数据说明。**
> 作者自己说"应该没问题"，在这套标准里等于什么都没说。

> 🔴 **硬规则（未取证不下结论、不许拿假设当结论）在 HABITS 的「红线」节，那里是权威副本。** 本 skill 讲的是怎么做到。

## 一、写的时候：测试驱动

- **先写测试、亲眼看它失败，再实现让它通过。** "亲眼看它失败"不是仪式——**没见过红的测试，你不知道它究竟测没测到东西**。
- **分层要齐**：单元、集成都要有，端到端覆盖**关键用户路径**。
- **可按比例从轻**：文档、配置、单行修复等低风险改动不必上全套。判据是**改动的爆炸半径**，不是改动的行数。

## 二、机器能查的不留给人查

lint、格式化、类型检查、静态分析**接入 CI 作为门禁**——不是"建议跑一下"，是不过不给合。

- 项目有现成配置就**遵守**，没有就**补最小集**。
- 判据一句话：**任何一条能被脚本判定的规则，都不该消耗人的注意力。** 人的注意力留给机器判不了的东西（意图对不对、抽象合不合理、边界想没想全）。

## 三、验的时候：对抗性审查

自验只能证明"我想到的都对"，证明不了"我没想到的"。所以要有**找茬的和写码的不是同一个脑子**。

- **收敛判据成文**：不设固定轮数上限，**审到连续一轮再无实质新发现为止**。
- **慢工出细活**：前期多审一轮，后期少返工十倍。
- 怎么组织多路独立审查：Claude Code 上用 `zephyr-workflow-orchestration` 编排（多 lens 并行找茬 → 逐条对抗验证杀误报）；其他引擎上用等价的多轮独立审查——**换的是编排工具，不是这条纪律**。

⚠️ **审查产出不是事实。** 任何 agent / 工具报出的 finding 都是**待验证输出**，必须逐条 verify 才能采信，别直接转述。

## 四、排查问题：三条纪律

| 纪律 | 含义 |
|---|---|
| **未取证不下结论** | 查数据库、查 git log、查日志、做调研，**拿到证据再说话** |
| **假设必须带验证** | 可以提假设（"可能是缓存问题"），但**必须同时给出验证动作并立刻取证**；不允许拿假设当结论 |
| **不确定就说不确定** | 证据穷尽仍不确定时，**带证据与置信度**如实汇报（"日志显示 X，尚未排除 Y，需要 Z 确认"），不装确定 |

第二条最常被违反，而且违反得很隐蔽：**"应该是 XX 导致的"这句话本身没错，错在说完就往下走了。** 说了假设就得立刻去验，验不了就标明"未验证"。

## 什么算"验过了"

合格证据的形态（**"应该没问题""已验证"不是证据**）：

- **可复现的命令 + 它的真实输出**，不是转述
- **计数型硬数字**：`单测 55 → 63 全绿（新增 8）`、`4/4 零失败`
- **正 / 负 / 边界三批样本**各多少条、各什么结果
- **引用带定位**：`文件:行号` + commit hash
- **否定式证据也要报**：没能触发的场景**点名说明「未触发 + 原因」**，不硬凑覆盖率——诚实的部分覆盖比虚假的全绿有用得多

## 反模式

❌ 写完实现再补测试 → 没见过红的测试不知道测没测到东西。
❌ lint 规则靠人在 review 里挑 → 能被脚本判的就进 CI 门禁。
❌ 自己审自己的代码就算审过了 → 找茬的和写码的不能是同一个脑子。
❌ 审查定"审三轮"然后收工 → 按收敛判据停，不按轮数。
❌ 直接转述 agent 报的 finding 当结论 → 那是待验证输出，逐条 verify 才算数。
❌ "应该是缓存问题" 说完就继续往下做 → 提了假设就立刻验，验不了就标"未验证"。
❌ 汇报里写"已验证 / 应该没问题" → 给命令、给输出、给数字、给 `文件:行号`。
❌ 为了让覆盖率好看，把没触发的场景说成通过 → 点名报未触发及原因。

## 常见问题

| 症状 | 原因 | 解决 |
|---|---|---|
| 测试全绿但线上还是炸 | 只测了想到的路径 | 叠对抗性审查，专门找"没想到的" |
| 审查没完没了 / 草草一轮就停 | 没定收敛判据 | 连续一轮零新发现即停 |
| 审查报了一堆问题，改完发现一半是误报 | 把 finding 当事实了 | 逐条 verify，CONFIRMED 才动手 |
| 排查绕了半天回到原点 | 拿假设当结论往下推 | 每个假设立刻配验证动作 |
| 汇报被质疑"你怎么知道的" | 给的是判断不是证据 | 按上面的证据形态给 |
