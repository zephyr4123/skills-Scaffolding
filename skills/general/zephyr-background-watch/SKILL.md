# zephyr-background-watch：让长任务跑完来找你

> **适用引擎：Claude Code 专属。** 依赖 `Monitor` 与后台 Bash 两个 harness 能力。Codex 侧是否有等价物**未核实**——没验证过就别声称能用。

> **心法：外部系统不会通知你。不问就不知道,而"不知道"在长任务上很贵。**
> 典型代价:托管出去的 agent 半小时前就干完在等验收,你这边还以为在跑;CI 早就红了,你还在等它绿。

## Step 0 · 先分清谁会自动叫醒你

这一步最常被跳过,跳过就会误以为"跑完了会有人告诉我"。

| 你起的活 | 跑完会不会自动通知你 |
|---|---|
| Workflow / Agent 工具 | ✅ harness 托管,完成即叫醒 |
| 后台 Bash（`run_in_background`） | ✅ 进程退出即叫醒 |
| **外部系统上的任务**（看板 / 工单 / 远程 agent） | ❌ 跟你的会话零连接 |
| **CI / 部署 / 远程队列** | ❌ 同上 |
| 别人机器上的 daemon | ❌ 同上 |

**判据一句话:不是这个 harness 起的,就不会来找你。**

⚠️ 别把外部系统自己的订阅功能当成通知你。它推的是**它自己的**收件箱/邮件,不进你的会话。

## Step 1 · 按"要几次通知"选形状

| 要什么 | 用什么 | 命令要求 |
|---|---|---|
| **一次**（"好了叫我"） | 后台 Bash | 条件满足即 **exit** 的命令,如 `until <cond>; do sleep 5; done` |
| **每次发生,无尽头** | Monitor | 无界命令(`tail -f` / `while true` 轮询) |
| **每次发生,有明确终点** | Monitor | 会自行 exit 的循环 |

**★ 别用无界命令去要"一次通知"。** `tail -f`、`while true` 永远不会自己退出,事件早就发生了,监控还挂在那儿直到超时。
（注意 `tail -f log | grep -m 1 X` **修不好**这个问题:日志之后若静默,`tail` 收不到 SIGPIPE,管道照样挂住。）

## Step 2 · ★ 静默 ≠ 正常（这一步最容易漏,也最贵）

设计监控时最自然的写法,是监听**成功路径的变化**。问题在于:

> **卡在中间态的失败,和"还在正常跑",在监控看来长得一模一样——都是没有新事件。**

**动手前必须自问一句:如果这东西现在挂了 / 卡死了 / 没人接,我的过滤器会吐出任何一行吗?** 答案是"不会"就得加哨兵。

### 中间态哨兵

只监听"状态迁移"是不够的——**永远迁移不出去**才是最常见的失败。给每个中间态配一个"停留过久"阈值:

```
in_progress 超过 N 分钟没更新  → 可能挂死
todo/queued 超过 M 分钟没认领  → 没人接（算力掉线？绑错了执行者？）
```

阈值按**正常耗时**定,不是拍脑袋:正常秒级认领的,5 分钟就该报;正常跑十几分钟的,25 分钟才报。

### 实战两例（都是真踩的）

**① 只盯一个中间态,漏掉最常见的那个。**
第一版哨兵只盯 `in_progress` 挂死,漏了 `todo` 无人认领——而后者恰恰是那个系统最常见的故障形态(执行方掉线 / 任务绑在离线的执行者上)。**没人认领和一切正常,在"只监听状态变化"的监控里完全同形。**

**② 拿不唯一的标识判定状态。**
push 之后立刻查"最新一条 CI run"——那一刻新 run 还没注册,**取到的是上一次的终态**,于是判定"成功"提前退出,而真正的 run 还没开始。
→ **按唯一标识匹配**(commit SHA / 任务 id),别用"最新一条"这种会滑动的坐标。这个病和"盯板空转"同根:**用不唯一的东西判定状态**。

## Step 3 · 轮询脚本的工程纪律

- **只发变化,不发全量。** 每行 stdout = 一条会话消息。**首轮只建基线不输出**,否则一起手就刷屏。
- **哨兵要去重。** "停留过久"若不记状态,每一轮都会报一次。报过就打标,离开该状态时清标。
- **行缓冲**:`grep` 要 `--line-buffered`,`awk` 要 `fflush()`。**`| head -N` 不能用**——它根本不 flush,会攒够 N 条才吐、然后掐断流。
- **轮询节奏**:远程 API **30s 起步**(有限流),本地检查 0.5–1s。
- **容错**:`curl ... || true`,单次请求失败不该杀掉整个监控。解析失败也要安全跳过。
- **过语法闸再上**:`bash -n <脚本>` / `node --check`,便宜得几乎免费,而监控挂了你是不会收到通知的（它本来就是靠沉默工作的）。
- **改监控要先停旧的**,否则两个实例重复报。

## 照抄模板：轮询外部看板 + 双哨兵

```bash
#!/bin/bash
STALL_MIN=25   # 干活中但长时间无更新 → 可能挂死
TODO_MIN=5     # 待认领超时 → 没人接
prev=""
declare -A flagged

snapshot() {
  # 输出:  id \t 状态 \t 摘要 \t 停留分钟数(仅中间态)
  <你的只读查询命令> 2>/dev/null | <解析成上述四列> || true
}

while true; do
  cur="$(snapshot)"
  if [ -n "$cur" ]; then
    if [ -z "$prev" ]; then
      prev="$cur"                                  # 首轮只建基线,不刷屏
    else
      while IFS=$'\t' read -r id st summary age; do
        old=$(echo "$prev" | awk -F'\t' -v k="$id" '$1==k{print $2}')
        [ "$old" = "$st" ] && continue
        if [ -z "$old" ]; then echo "🆕 ${id} 新建 [${st}] ${summary}"
        else
          case "$st" in
            <要你介入的态>) echo "🔔 ${id} ${old} → ${st} 等你处理 | ${summary}" ;;
            <失败态>)       echo "🚧 ${id} ${old} → ${st} | ${summary}" ;;
            *)              echo "↻ ${id} ${old} → ${st} | ${summary}" ;;
          esac
        fi
      done <<< "$cur"
      prev="$cur"
    fi

    # 双哨兵:两种静默失败都要覆盖,每条只报一次
    while IFS=$'\t' read -r id st summary age; do
      case "$st" in
        <干活中>) limit=$STALL_MIN; hint="卡在 ${st} ${age} 分钟没更新,可能挂死" ;;
        <待认领>) limit=$TODO_MIN;  hint="停在 ${st} ${age} 分钟没人认领,查执行方在不在线" ;;
        *)        unset 'flagged[$id]'; continue ;;
      esac
      if [ -n "$age" ] && [ "$age" -ge "$limit" ] && [ -z "${flagged[$id]}" ]; then
        echo "⚠️ ${id} ${hint} | ${summary}"
        flagged[$id]=1
      fi
    done <<< "$cur"
  fi
  sleep 30
done
```

按 `persistent: true` 挂上去,它就一直盯到你 `TaskStop` 或会话结束。

## 硬性规则

1. **不是本 harness 起的活,就不会来通知你** — 外部系统一律要自己架监控,别假设"跑完会有人说"。
2. **要一次通知就用会自己 exit 的命令**（后台 Bash + until）;无界命令只配 Monitor。
3. **★ 静默 ≠ 正常** — 上线前自问「现在它挂了,我的过滤器会吐出任何一行吗」;不会就加中间态哨兵。
4. **每个中间态都要配停留阈值** — 只盯一个会漏掉最常见的那种失败。
5. **状态判定用唯一标识**（SHA / id),绝不用"最新一条"这类会滑动的坐标。
6. **只发变化、首轮建基线、哨兵去重** — 每行都是一条会话消息,刷屏的监控会被自动停掉。
7. **过语法闸再挂上** — 监控挂了不会有人通知你,它本来就靠沉默工作。

## 反模式

❌ 起了外部长任务就等着"跑完通知" → 不会有通知,自己架监控。
❌ 用 `tail -f` / `while true` 去要一次性通知 → 永不退出,挂到超时。
❌ 只监听"成功路径的状态变化" → 挂死 / 无人认领全部静默,和正常运行同形。
❌ 只给"干活中"配挂死阈值,不管"待认领" → 漏掉最常见的那种失败。
❌ push 完立刻取"最新一条 run" 判定结果 → 新 run 还没注册,取到上一次的终态,提前误判成功。
❌ 首轮就把全量状态吐出来 → 一起手刷屏,还淹掉真正的变化。
❌ 哨兵不去重 → 每轮报一次,变成噪音源。
❌ 管道里 `| head -N` → 不 flush,攒够才吐还掐断流。
❌ 远程 API 用 1s 轮询 → 撞限流,而且没必要。
❌ 改完监控脚本直接挂,不过 `bash -n` → 挂了你收不到任何通知。

## 常见问题

| 症状 | 原因 | 解决 |
|---|---|---|
| 外部 agent 早干完了我才发现 | 没架监控,靠记得回去查 | 架 Monitor,把"记得查"变成"它来找我" |
| 监控一直不结束,事件早过了 | 用无界命令要一次性通知 | 换后台 Bash + `until` 循环 |
| 一切安静,以为在跑,其实卡死了 | 只监听状态迁移,没设中间态哨兵 | 给每个中间态配停留阈值 |
| 任务永远没人接,监控一声不吭 | 哨兵只覆盖了"干活中" | 给"待认领"也配阈值 |
| CI 明明还没跑就报成功 | 用"最新一条 run"判定 | 按 commit SHA 匹配 |
| 监控疯狂刷屏被自动停掉 | 发了全量 / 哨兵没去重 | 首轮建基线 + 报过打标 |
| 匹配到了但一直不见事件 | 管道某级没行缓冲 | `grep --line-buffered` / `awk` 加 `fflush()`,别用 `head` |
| 同一件事被报两遍 | 改监控时没停旧实例 | 先 `TaskStop` 再挂新的 |
