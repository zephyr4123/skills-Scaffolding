# zephyr-nested-git：外层仓管协作，代码仓各管各的

> **心法：多仓关联的本质是选「指针精度」。** submodule 把指针锁到提交级，nested 指针只锁到仓库级。
> 锁得越松，两层越解耦；但松掉的每一格都必须有东西补位 —— manifest 记线上坐标、CLI 把红线写进代码、issue 串起跨仓变更。补位缺一个，「松」就变成「失控」。

## 一、这是什么，什么时候用

拓扑长这样：

```
product/                    ← 外层协作仓（GitHub / Gitee / 任意平台）
├── repos.json              ← 指针 manifest：多仓拓扑的唯一真相源
├── .gitignore              ← 挡住下面全部代码目录
├── repos*                  ← 跨仓运维 CLI（照 references/ 生成，归项目所有）
├── docs/  research/  …     ← issue 台账、跨端文档、立项产物
├── ios/                    ← 独立 git 仓（可以在完全不同的平台，如自托管 GitLab）
├── android/                ← 独立 git 仓
└── backend/
    ├── api-service/        ← 独立 git 仓
    └── billing-service/    ← 独立 git 仓
```

`ios/` 这些目录**物理上**在外层仓的目录树里，但对外层 git 完全不存在——`.gitignore` 整目录挡掉，`git ls-files` 里一行业务代码都没有。每个代码目录自己是完整 git 仓，各自 commit、push 回各自远端，CI 照旧触发，**外层毫不知情**。两层之间唯一的纽带是 manifest 里的坐标。

### 和其它方案的判据表

| 方案 | 指针精度 | 跨仓原子提交 | 两层耦合 | 典型死法 |
|---|---|---|---|---|
| 合仓（真 monorepo） | —（同一历史） | 有 | 完全耦合 | 迁移期要重配所有 CI、断掉所有人的工作副本 |
| `git submodule` | 提交级 | 有（外层锁 SHA） | 紧：内层每动一步外层跟着提交 | 忘了 `submodule update` 的同事拿着旧代码干活 |
| `git subtree` | 提交级（双向同步） | 有 | 紧：历史互相写入 | 两边共管的文件（CI 配置等）持续冲突；`subtree split` 每次重算 hash，回推要 `--force` |
| **nested 指针** | **仓库级** | **无（靠 issue 补位）** | **零：互不知情** | 本地分支 ≠ 线上分支，grep 出错误结论（见第五节，有护栏） |

### 适用前提（三条都占才值得用）

1. **外层与代码仓在不同平台 / 不同凭据 / 不同受众**——比如外层在 GitHub 管协作与 issue，代码在公司自托管 GitLab 走各自 CI。平台一致时 submodule 的成本会低很多。
2. **各代码仓已有自己的 CI 与发版节奏**，动不得、也不想动。nested 方案对现有 CI 的改动是零。
3. **需要一个「项目之家」**放不属于任何单个代码仓的东西：issue 网络、跨端文档、运维 CLI、立项期产物。对 agent 尤其友好——外层仓小，新会话拉下来只有坐标 + 文档，不会被几十万行业务代码淹掉上下文。

### 反判据（占一条就别用）

- 需要跨仓原子提交或统一版本快照 → submodule 或合仓
- 只有一个代码仓 → 直接合仓，别造拓扑
- 外层要参与代码构建 → 这套的外层是纯协作层，构建依赖会把「互不知情」的前提拆掉

## 二、三个零件

### 零件 1：外层仓——角色边界写死

外层仓**只追踪**：指针 manifest、运维 CLI、文档 / issue 台账 / 立项产物、`.gitignore` 本身。判据一句话：**`git ls-files` 的输出里不允许出现任何业务代码。** 一旦有人往外层塞了代码，两层解耦的全部前提就开始漏。

### 零件 2：`.gitignore` 挡位

```gitignore
# ── 嵌套独立 code git（外层不追踪，各自推各自的远端，坐标见 repos.json）──
/ios/
/android/
/backend/
```

注意用**整目录**挡，不要按文件模式挡——挡位的语义是「这个目录归另一个 git 管」，不是「这些文件不重要」。

### 零件 3：指针 manifest（`repos.json`）

```json
{
  "_note": "多仓拓扑 + 线上坐标的唯一真相源，跨仓 CLI 全部命令读这里。改拓扑改这个文件，不改 CLI 代码。",
  "repos": {
    "ios": {
      "url": "https://git.example.com/products/demo/ios.git",
      "path": "ios",
      "prod_branch": "main",
      "prod_version": "1.4.2"
    },
    "api-service": {
      "url": "https://git.example.com/products/demo/api-service.git",
      "path": "backend/api-service",
      "prod_branch": "main"
    }
  }
}
```

四条设计约定，每条都有理由：

- **`_` 开头的键是注释**，工具一律跳过。JSON 没有注释语法，而 manifest 恰恰是最需要「为什么长这样」留痕的地方——坐标背后的取证过程写进 `_note`，比丢进聊天记录强。
- **`url` 是权威**。CLI 每次网络操作前把 `origin` 归正到 manifest 里的 url（防手工改 remote 后的漂移；平台只通一种协议时，把 manifest 写成那种协议即可，比如某些自托管实例前置了 CDN、SSH 端口根本不通，就统一写 https）。
- **`prod_branch` / `prod_version` 记「线上跑的是哪条分支哪个版本」**。这是 nested 方案松掉提交级锁定之后**必须补的那格**：外层不知道内层停在哪，那至少要知道线上在哪。它的存在理由见第五节的事故。
- **改拓扑改 manifest，不改 CLI 代码**。加第五个仓 = 加一段 JSON。CLI 里不允许硬编码仓名；要按仓分类做能力分流（比如某类动词只对服务端仓有意义），加 `kind` 之类的字段靠数据过滤。

## 三、落地：两条路径

### Greenfield（新项目初始化）

1. 建外层仓，写 `repos.json`（此刻可能只有一个仓，也照写——拓扑从第一天就有唯一真相源）
2. `.gitignore` 挡住全部代码目录位
3. 照 `references/repos-cli-reference.py` 生成项目内 CLI（如命名 `./repos`），跑 `./repos doctor` 验证 manifest 合法
4. `./repos clone all` 把代码仓解引用到位

### 承接（接手一个已有的 nested 拓扑项目）

1. `git clone` 外层仓——**拿到的是没有代码的骨架，这是预期不是故障**
2. `./repos clone all`——CLI 读 manifest，把缺的仓逐个 clone 到位（幂等，重复跑无害）
3. `./repos status`——看四件事：各仓在哪条分支、是否追平远端、有没有脏文件、**本地分支是不是线上那条**

承接体验是这套方案的试金石：如果新人 clone 下来要靠问人才知道代码在哪，manifest 就没写全。

## 四、动词与红线（核心节）

跨仓 CLI 的每个动词都必须带自己的防护。这些防护不是防御性编程的洁癖——**每一条背后都有一种真实事故形态**，写在代码里而不是文档里，是因为「机器判不了的规矩不是规矩」。

| 动词 | 作用 | 红线 |
|---|---|---|
| `doctor` | manifest 合法性 + 各仓 clone 态 + remote 一致性 | 只读；发现问题给下一步命令，不自动修 |
| `clone <仓\|all>` | 把缺失的仓 clone 到位 | 幂等；**目录非空但不是 git 仓 → 拒绝碰**，留人工确认 |
| `status` | 各仓分支 / 领先落后 / 脏数 一屏总览 | 本地对账不联网；**prod_branch 漂移必须告警** |
| `fetch / sync <仓\|all>` | 更新远端跟踪 ref + 领先落后对账 | **fetch 失败绝不吞**——失败的仓不出对账数字 |
| `pull <仓\|all>` | 快进本地分支 | 只 `--ff-only`，绝不自动 merge / rebase |
| `push <仓\|all>` | 推当前分支 | 只 fast-forward；**代码路径里不存在 `--force`**；脏仓拒推；detached HEAD 拒推 |
| `remotes [--fix]` | remote 与 manifest 对账 | 默认只报告，`--fix` 才归正 |

逐条展开红线背后的事故形态：

**`clone` 非空拒碰。** 目录里有东西但没有 `.git`，说明有人手工放过文件或上次 clone 断在半路。盖掉它可能销毁没提交的工作——宁可停下来要一次人工确认。

**`status` 的「同步」有两义，必须拆开。** `rev-list --left-right --count origin/br...br` 算出的「同步」只表示**本地分支追平了它自己的远端**，完全不表示这条分支就是线上跑的那条。这两件事混在一起就是第五节那起事故。所以 status 在对账之外必须比对 `prod_branch` 并告警。

**`sync` 的 fetch 失败绝不能吞。** fetch 挂了的话，远端跟踪 ref 停在上次成功的状态，此时算出的「同步 / 落后 N」是**基于陈旧数据的肯定结论——比报错更危险**。正确行为：该仓打红字「不做对账」，退出码非 0。

**`pull` 只 `--ff-only`。** 自动 merge 会在用户没看着的时候制造合并提交；分叉了就该停下来让人处理。

**`push` 的三道闸。** ① 脏仓拒推——防「以为都提交了」；② detached HEAD 拒推——`rev-parse --abbrev-ref HEAD` 在 detached 状态下返回字面量 `HEAD`，把它当分支名传给 `pull origin HEAD` 会拉远端默认分支并快进过去，**正在 bisect / 对着 tag 复现问题的现场会被静默销毁**，所以 branch() 函数必须把 detached 显式返回 None 逼调用方处理；③ 用完整 refspec `refs/heads/br:refs/heads/br` 写死源和目标，不让分支名被 git 再解析一遍。

**`push` 永不 `--force`，被拒的 SOP 是「合进来 → 重跑门禁 → 再推」。** 事故形态：远端多出同事的提交（比如 CI 配置升级），裸 `push -f` 会把它静默盖掉，要等下次流水线跑挂才发现。这是典型的「歪路收益当场兑现、代价延后转嫁给别人」——修路救不了，只能焊死：让这个选项在代码里不存在。

**写操作拒绝 `all`。** 曾经的实现里，写类动词传 `all` 会静默只处理第一个仓、其余一个字不提——操作者以为「全推了」，实际漏推，跨仓联动变更就会在线上跑成版本不匹配。git 动词里 push 逐仓打印所以可以收 `all`；但凡是**输出不逐仓明示的写动作**（部署类尤其），必须逐个点名。

**失败一律非 0 退出码。** 上层脚本和 agent 靠退出码判断成败；吞异常等于让它们拿着假成功继续跑。另一个隐蔽形态：命令 handler 忘写 `return`，Python 默认返回 None、进程退出码 0——**「没写返回值」就是「永远成功」**。dispatcher 层要兜住这个。

## 五、结构性代价与补偿

选仓库级指针，有两笔账必须认，并且各配一个补偿机制：

### 代价 1：工作副本 ≠ 线上（最大的坑）

事故形态：承接期在某端的本地 `main` 上 grep，发现没有某功能，据此写下「这一端根本没有 X 功能」并往下推了一串结论——而线上跑的是另一条 feature 分支，功能全在那上面。错误结论一路传导，最后是数据侧的异常反过来揪出了代码侧的错。

根因：**`grep` 查的是工作副本，不是线上产物**，而 nested 方案的外层不锁提交，没有任何机制保证你 checkout 的分支就是线上那条。

补偿：manifest 记 `prod_branch` / `prod_version`，`status` 每次比对本地 HEAD 并告警。纪律配套：凡「某端没有某功能 / 某字段」这类**否定判断**，先看 status 有没有红字、再 `git branch -r` 扫一眼有没有更新的分支，别只信当前工作副本。另外：`prod_branch` 的值最好有发布标记（tag）背书；代码仓不打 tag 的话它只是取证推断，要在 `_note` 里写明证据来源。

### 代价 2：没有跨仓原子提交

一个改动同时动 iOS + 服务端时，两边是两条互不知情的提交，没有任何 git 机制把它们绑在一起。

补偿：**靠 issue 串**。跨仓变更必须有一条 issue 作为锚点，两边的 commit message 都引用它；要回答「这个功能改了哪些仓」，查 issue 不查 git log。这不是权宜——协作层的关联本来就该在协作工具里，git 只是其中一个执行面。

## 六、从 git 动词往上长：运维台 CLI 的通用纪律

外层仓的 CLI 往往不止管 git——部署、CI 观测、日志、数据库只读入口都会长在上面。这些动词平台相关，不进本 skill 的参考实现，但设计纪律是通用的：

- **拓扑读 manifest，改坐标改 json 不改代码**——所有动词共享同一个真相源，加仓 / 改地址零代码改动。
- **危险动作 dry-run 默认，真执行要显式 confirm；生产环境要独立的 confirm 参数**——`--env prod --confirm` 仍然是 dry-run、必须 `--confirm-prod` 才真动，这是防手滑不变式：肌肉记忆里的 `--confirm` 不会误伤生产。
- **审的和发的必须是同一个**——dry-run 给出带具体执行对象 ID 的完整命令行，真执行必须回传这个 ID 并校验一致。防的是「审的是 A、发的是 B」：dry-run 和 confirm 之间隔着人的思考时间，够别人合一个变更进来。
- **凭据只进内存与请求头 / 子进程环境，不落地、不回显、不进 argv**（argv 对本机全部进程可见）；所有输出过统一的 mask()；**HTTP 客户端拒绝跟随重定向**——3xx 会把 Authorization 头原样发去重定向目标，这类泄露发生在网络层，输出侧的 mask() 兜不住。
- **驱动而非复刻**——部署逻辑在 CI 侧维护、跑在 runner 上，本地 CLI 只触发和观测，本地零云凭据。复刻部署逻辑等于永久背上两份实现的同步义务。
- **权限动词按协作关系裁剪，不按技术能力裁剪**——作为协作方就算 token 权限够，也只提供「建 MR / 看 MR」，永远不提供 merge。动词表就是权限声明。

## 七、扩展点：建 MR / PR 的四道校验

如果给 CLI 加 `mr` 动词（对接 GitLab 类平台 API），四道校验是必需品不是防御性编程：

1. **源分支必须在远端存在**——GitLab **不校验**这一点：拿不存在的分支名 POST `/merge_requests` 照样返回 201，建出一条没有任何变更的空壳 MR，还得道歉关闭（彻底删除通常要 Owner 权限）。
2. 源 ≠ 目标。
3. **相对目标必须有领先提交**——否则是空 MR，纯噪声。
4. **同源分支已有 open MR 就不重复建**，直接把已有链接打出来。

建完把 `web_url` 单独一行显眼打印，方便直接甩给评审。

## 八、references/ 怎么用

- `repos-cli-reference.py`——单文件参考实现，纯 Python 标准库 + git，覆盖第四节全部动词与红线。**用法是照它生成项目内的 CLI**（拷进外层仓根、改名 `./repos`、按需调 MANIFEST 路径），不是从 skill 目录直接运行——CLI 归项目所有、随外层仓一起进版本控制，项目不应依赖「这台机器装了本 skill 库」。
- `repos-example.json`——manifest 示例，含注释键约定。

改编时的底线：第四节的红线一条都不许删。可以加动词、加字段、换语言，但「pull 只 ff-only / push 永不 force / fetch 失败不吞 / 非 0 退出码 / prod 漂移告警」是这套方案安全性的全部来源——删掉任何一条，剩下的就只是个批量 git 包装器。
