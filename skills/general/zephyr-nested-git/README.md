# zephyr-nested-git

> 把「外层协作仓 + 多个独立业务代码仓」的管理方式从一段真实的多端产品承接里蒸馏成可复用的拓扑方案 —— 外层零业务代码只存指针，代码仓互不知情各推各的远端；方法论 + 参考实现，红线写在代码里不写在墙上。

## 问题陈述

一个多端产品（iOS + Android + 若干后端服务）的代码分散在多个仓里，各有自己的 CI 和发版节奏；同时项目还需要一个「家」放不属于任何单个代码仓的东西——issue 网络、跨端文档、运维工具、立项产物。而且两层往往**不在同一个平台**：协作层想用 GitHub 的 issue 生态，代码层锁死在公司自托管 GitLab 上，凭据、受众、权限模型全都不同。

git 自带的两个答案在这个场景下都不好使：

- **submodule** 把指针锁到提交级，内层每前进一步外层都要跟着提交去更新 SHA；两层平台不同时，这个耦合把两套凭据、两套工作流缝在了一起。
- **subtree** 双向同步听着两全，实测两边共管的文件（CI 配置这类「归代码仓所有」的）持续冲突，`subtree split` 每次重算 commit hash、回推必须 `--force`，历史很快缠成一团。

而「把代码搬进外层合仓」要重配所有 CI、断掉所有人已 clone 的工作副本——承接期最不该引入的就是发布链路的不确定性。

## 解决方案

**nested-git 指针**：代码仓以独立 git clone 嵌在外层目录里，被 `.gitignore` 整目录挡住，对外层 git 完全不存在；「代码在哪」记在一个被追踪的 manifest（`repos.json`）里——url / path / prod_branch / prod_version，它是拓扑的唯一真相源。配一个项目内的跨仓 CLI（照 `references/` 的模板生成）承担 submodule 原生命令的职责，且每个动词都带自己的红线：

| submodule 原生 | 本方案 | 多出来的防护 |
|---|---|---|
| `submodule update --init` | `clone all` | 幂等；非空非 git 目录拒碰 |
| `submodule status` | `status` | 领先落后 + 脏数 + **prod_branch 漂移告警** |
| `submodule foreach git fetch` | `sync` | fetch 失败不吞、不出陈旧对账 |
| `submodule foreach git push` | `push` | 脏仓拒推、detached 拒推、完整 refspec、`--force` 在代码里不存在 |

## 核心立论

**指针精度是一个可选的设计维度，不是 git 给什么就用什么。** submodule 锁提交级、nested 只锁仓库级——把版本关联的精度主动降下来，换两层平台 / 凭据 / CI 的彻底解耦。

代价是显性的，且每笔都要补位：外层锁不住内层版本 → manifest 记 `prod_branch`、status 逢漂移必告警（否则会在本地旧分支上 grep 出「这一端没有某功能」的错误结论，一路传导）；没有跨仓原子提交 → 跨仓变更靠 issue 串锚。**放弃「git 帮你管」，换来的必须是「每个动词都能塞进自己的红线」**——补位机制一个不落，「松」才不会变成「失控」。

红线为什么必须在代码里：`push --force` 这类歪路收益当场兑现、代价延后转嫁给别人，修路救不了只能焊死；而「fetch 失败要报出来」这种规矩靠人记必然漂移——机器判不了的规矩不是规矩。

## 设计决策

| 决策 | 选择 | 原因 | 替代方案 |
|---|---|---|---|
| 形态 | 方法论 + `references/` 参考实现 | 红线（ff-only / 永不 force / 失败不吞 / 漂移告警）必须以代码形态交付，否则每次落地都重新发明、十条丢五条；但 CLI 归项目所有，照模板生成 | 纯 introduction —— 防护会丢；带可执行中央脚本 —— 项目依赖「装了 skill 库」这个前提，且要长期背中央维护 |
| manifest 格式 | JSON + `_` 前缀注释键 | JSON 无注释语法，而坐标恰恰最需要「为什么长这样」留痕（prod_branch 是取证推断还是权威声明，差别巨大） | YAML 有注释但多一层解析依赖；注释丢聊天记录 —— 下个承接的人看不见 |
| 参考实现依赖 | 仅 Python 标准库 + git | 参考实现的使命是「拷进任何外层仓就能用」，一个 pip 依赖都嫌多 | bash —— 数组 / 字符串处理写防护逻辑太脆；带依赖的 Python —— 违背可拷贝性 |
| `status` 联网否 | 本地对账不联网，`sync` 才 fetch | status 要快、要能离线跑；把「我的数据多新鲜」显式交给用户选 | status 顺带 fetch —— 慢，且网络抖动会让最常用的命令变得不可靠 |
| 写操作的 `all` | git 动词收 `all`（输出逐仓明示），并点名部署类写操作必须拒绝 `all` | 曾有实现对写类动词传 `all` 时静默只处理第一个仓 —— 操作者以为全发了，跨仓联动变更在线上跑成版本不匹配 | 一律拒绝 all —— push all 输出逐仓可见，风险形态不同，一刀切损失日常效率 |
| 范围 | 只到 git 动词 + MR 四道校验（prose） | 部署 / CI / 日志动词平台相关，进参考实现就要带 API 与凭据处理，破坏零依赖；其通用纪律以设计原则形态写进 SKILL.md 第六节 | 全栈运维台参考实现 —— 平台假设写死，迁移性反而变差 |

## 已放弃方案

### A：纯方法论文档，不带参考实现
- **是什么**：只写 SKILL.md，动词与红线全部以文字描述。
- **为什么放弃**：这套方案的安全性几乎全部住在防护细节里（detached HEAD 返回 None、fetch 失败不出对账、完整 refspec……），文字转代码的过程每次都有损耗。参考实现是把损耗压到零的唯一办法——agent 照抄一个能跑的模板，比照文字重写可靠一个量级。

### B：把参考实现做成 skill 自带的可执行工具
- **是什么**：CLI 放在 skill 目录里直接跑，项目里只留 manifest。
- **为什么放弃**：项目会依赖「这台机器装了 skill 库」，跨机器、跨引擎、多人协作全碎；且中央脚本要为所有项目的差异背长期维护。CLI 的正确归属是外层仓自己——随仓进版本控制，项目要怎么改就怎么改。

### C：把 MR / PR 校验也写进参考实现
- **是什么**：加 `mr` 动词，内置「源分支必须在远端存在」等四道校验。
- **为什么放弃**：要带平台 API、token 处理、分页——参考实现的零依赖与可拷贝性全没了。四道校验的价值在**知识**（GitLab 拿不存在的分支建 MR 会返 201 建出空壳），写成 SKILL.md 第七节的 prose 检查单，实现留给各项目按自己平台做。

## 蒸馏来源

从一段真实的多端产品承接实践中蒸馏：外层协作仓 + 多个平台隔离的代码仓，全套动词与红线在日常运维中实测踩坑后固化。所有事故均已泛化为形态描述，示例坐标均为虚构。
