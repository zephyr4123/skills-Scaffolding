# zephyr-ios-verify-loop

iOS 开发-验证闭环:**自己拿到证据再交付,别把验证甩给人。**

从一个真实产品(SwiftUI 客户端 + Python 引擎 + JVM 后端)六天连续交付里沉淀出来的方法论 —— 每一条配方和每一条坑都是实测踩出来的,不是设想。

## 心法

> **UI 上的每一次点击,都要能在数据库里找到那一行。**
> 开发与验证之间没有「等环境 / 等联调 / 等别人」的断点。

## 它解决什么

agent(或人)最常见的失败模式不是不会验,是**没查就说"我验不了"** —— 于是把验证成本转嫁给对方,让人一趟趟真机出图,而那些缺陷本可以在本地几分钟内暴露。

本 skill 的第 0 步就是钉死这条:**说「我验不了 X」之前,先花一条命令查工具链到底在不在。**

## 覆盖什么

| 步骤 | 内容 |
|---|---|
| **Step 0 · 先查再说** | 工具链 / 密钥 / 模拟器 / DB / 测试的体检清单,反「我验不了」 |
| **Step 1 · 按层取证** | 编译层 → 本地同镜像服务 → 模拟器点击驱动(AXe)→ 手势探针 → 接口正负边界样本 → 只读 SQL 对账 → CI/部署 gate |
| **Step 2 · 审查双轨** | workflow 对抗审查(跨层契约/状态机/竞态)+ 清单直审(view 层),收敛判据 = 连续一轮零新发现 |
| **Step 3 · 报证据** | 什么算合格证据;`文件:行号` + commit 的标准引用格式;**否定式证据也要报** |
| 附 | 全 App 逐屏截图审计(穷举驱动,非「想到哪截到哪」) |

## 几条最省时间的实测结论

- **编译通过 ≠ 验过**:一次 IA 重构 `BUILD SUCCEEDED` 且作者自读三遍,对抗审查仍逮出 2 个 blocker —— 编译器对事务竞态完全无感。
- **截图相同 ≠ 通过**:内容列限宽套错位置导致两侧成手势死区,截图上与正确实现一模一样,只有手势探针能抓。
- **别从截图反推坐标**:截图像素与 AX point 的换算比随机型 / 缩放 / 截图来源而变(窗口截图还含边框偏移),坐标一律取 `describe-ui` 的 AX frame。
- **tap 完必须验焦点再 type**:轮询 `UIKeyboardLayoutStar` 确认键盘起;不起再按 physical → touch → 冷启动 逐级退,别闷头重试。
- **`simctl defaults` 读的不是 app 沙箱域**:直读容器 plist,否则会把「功能正常」误判成「台账坏了」。
- **agent 的 finding 不是事实**:实测误报率约 37%,必须逐条 verify 再采信。

## 适用 / 不适用

- ✅ iOS(SwiftUI / UIKit)项目改完代码要自验、要做 UI 审计、要跑 E2E 取证
- ❌ 非 iOS 项目(AXe/simctl 那套不通用);纯文档改动

多 agent 编排本身怎么设计、怎么防挂,见 `zephyr-workflow-orchestration`。
